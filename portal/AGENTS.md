# Slapdash portal (`portal/`)

The Slapdash portal is the control plane: a self-hosted Ash + Phoenix
application that manages users, tenants, instance configuration, software
repositories and the applications running from them. Monorepo-wide
rules live in [`../AGENTS.md`](../AGENTS.md); this file adds the rules for
`portal/`. Run every command below from `portal/`.

## Stack

- Elixir 1.20 on Erlang/OTP 29
- Phoenix 1.8 with LiveView 1.2, served by Bandit
- Ash 3 with AshPostgres (PostgreSQL 17 or later) and AshPhoenix
- Layered, classless CSS and homegrown components. Do not add a CSS framework
  or component kit such as Tailwind or daisyUI.
- esbuild, run as a standalone binary by the `:esbuild` Mix package, bundles
  `app.js` and `app.css`, so there is no Node.js toolchain or `package.json`

## Layout

- `lib/slapdash/` holds the domain layer: Ash domains and resources, the
  `Slapdash.Repo`, and OTP processes. A domain is `lib/slapdash/<domain>.ex`
  and its resources sit in `lib/slapdash/<domain>/`.
- `lib/slapdash_web/` holds the web layer: router, controllers, LiveViews and
  components.
- `priv/repo/migrations/` and `priv/resource_snapshots/` are generated by
  `mix ash.codegen`. Commit them together.
- `test/` mirrors `lib/`. `test/support/` holds `Slapdash.DataCase` and
  `SlapdashWeb.ConnCase`.
- `rel/` customises the Mix release: `overlays/bin/migrate` and
  `overlays/bin/server` are the production entry points, and `env.sh.eex`
  sets release environment defaults.
- `nix/` holds the Nix package, NixOS module, container image, dev shell and
  VM test. The root `flake.nix` wires them up; see `../AGENTS.md`.
- `docs/` holds the documentation, in one directory for each Diataxis type:
  `tutorials/`, `how-to/`, `reference/` and `explanation/`.

Development and test use PostgreSQL on `localhost` with user and password
`postgres` (`config/dev.exs`, `config/test.exs`).

## Configuration

- Environment variables are only for what the app needs before it can reach
  its database: `DATABASE_URL`, `SLAPDASH_MASTER_KEY`, `PORT` and a few
  database knobs, read with `Shoddy.Env` in `config/runtime.exs`. README.md
  lists them; keep that list current. Do not add a variable for anything that
  can live in the database.
- Everything else an operator sets up (public URL, mail, GitHub sign-in,
  tenants) is an Ash resource in the `Slapdash.Instance` or
  `Slapdash.Tenancy` domains, edited by root in the admin pages. One-row
  resources use an integer primary key fixed at 1 with a check constraint,
  a `:current` read action, and `:configure`/`:reconfigure` actions.
- Connections to outside services, repositories and bot enrollments are Ash
  resources too (`Slapdash.Connections`, `Slapdash.Repositories`,
  `Slapdash.Bots`), edited by tenant administrators in the tenant pages.
- `secret_key_base` and the token signing secret are generated on first boot
  and stored encrypted (`Slapdash.Instance.Boot`, `BootSecrets`). Code that
  needs them reads the application environment, which `Boot` fills.
- Read config at the point of use (`Slapdash.Mailer`, `Slapdash.Secrets`),
  so changes apply without a restart.
- Operator tasks live in `Slapdash.Release` and must work from
  `bin/slapdash eval` with no running node, so they work before the server
  is up. The NixOS module and the container run Erlang distribution on
  loopback only (node `slapdash@127.0.0.1`, cookie in a file the service
  user owns), so `rpc` and `remote` also reach a running server.

## Sign-in

- Sign-in is by invitation only. Keep `registration_enabled? false` on every
  AshAuthentication strategy, and do not add a sign-up page or a register
  action. Users are created only by `Slapdash.Accounts.ensure_user/1`,
  after the caller is authorized (adding a member, or `create_root` from the
  console).
- Sign-in pages and messages must not show whether an email has an account.

## Definition of done

- `mix precommit` passes with no warnings.
- New behaviour has tests. Test through domain code interfaces and
  `Phoenix.LiveViewTest`, not through private functions.
- If you changed resources, the migrations and snapshots from
  `mix ash.codegen <name>` are committed and you have read them.

## Ash conventions

- All data access and business logic go through Ash. The web layer calls the
  code interfaces defined on domains (`define :create_repository, ...` in the
  domain's `resources` block). It never calls `Slapdash.Repo`, `Ecto.Query`
  or `Ash.Changeset`/`Ash.Query` directly.
- Create domains and resources with `mix ash.gen.domain` and
  `mix ash.gen.resource`. They register domains in `config :slapdash,
  :ash_domains` for you. If you add a domain by hand, register it there too.
- Write explicit, named actions that say what they do (`:archive`,
  `:deploy`), not generic `:update` actions with many accepted fields.
- Never write migrations for resource tables by hand. Change the resource, run
  `mix ash.codegen <name>`, then read the generated migration. For SQL that
  codegen cannot express, prefer `custom_statements` in the resource's
  `postgres` block.
- Use `AshPhoenix.Form` for forms backed by actions.
- Add authorization policies to every resource that is reachable from the
  web. Slapdash runs deploys and holds credentials, so deny by default.
- Authorize with `Slapdash.Authz`, our own scheme modelled on ash_grant (see
  "Authorization" below), not ad hoc checks.
- Ash's documentation is split into sub-rules, linked at the end of this file.
  Read the relevant one before using a feature (actions, relationships,
  calculations, policies and so on). Do not rely on memory of Ash 2 APIs.

## Authorization

`Slapdash.Authz` is our own permission scheme, shaped like ash_grant so a
later move is mostly mechanical. Do not add ash_grant itself.

- Roles are in `Slapdash.Authz.Roles` as permission strings,
  `[!]resource:instance:action:scope` (instance is always `*` for now). Root
  is install-wide (`User.root`). Administrator and engineer are per tenant
  (`Slapdash.Tenancy.Membership`). Every signed-in user also gets the
  `signed_in` permissions. Change roles there, in code.
- A resource opts in with `extensions: [Slapdash.Authz.Resource]` and an
  `authz` block (`resource_name`, `tenant_attribute`, `scope` filters), then
  authorizes reads with `Slapdash.Authz.FilterCheck` and creates, updates and
  destroys with `Slapdash.Authz.Check`.
- A tenant role only ever reaches its own tenant: rows in its schema for
  `multitenancy strategy :context` resources, or rows whose
  `tenant_attribute` is its tenant for public-schema resources. A resource
  with neither is out of reach of tenant roles. Deny wins over allow.
- Test policies through code interfaces with real actors (see
  `test/slapdash/authz_test.exs`).

## Multitenancy

- Isolate tenant data with context-based multitenancy
  (`multitenancy strategy :context`). Do not use `strategy :attribute` for
  tenant data. Each tenant has one PostgreSQL schema, `tenant_<slug>`,
  created by `Slapdash.Tenancy.Tenant` with `manage_tenant`. Pass the tenant
  record as `tenant:`; `Ash.ToTenant` turns it into the schema.
- Install-wide data (users, instance settings, the tenant list, memberships)
  lives in the `public` schema.
- Tenant pages are at `/<slug>/<page>`, and at `/<page>` on the tenant
  subdomain when root turns subdomains on. `SlapdashWeb.TenantScope` loads
  `@tenant` and `@tenant_prefix`. Build links between tenant pages with
  `tenant_path(@tenant_prefix, ~p"/<page>")`. The tenant routes come last in
  the router; add the first part of each new top-level route to
  `Slapdash.Tenancy.Validations.NotReserved` (a test checks this).
- Tenant data that an incoming request must find before it knows the tenant
  (connections and repositories) also lives in the `public` schema, with a
  `tenant_id` and `authz tenant_attribute`.
- A table in a tenant schema has no foreign key to a `public` table. Such a
  key makes each tenant migration lock the public table, and parallel tenant
  creation can then deadlock. Use `reference :name, ignore?: true`, and for
  versions use `mixin {Slapdash.Versions, :mixin, ["<name>", [tenant?: true]]}`
  with `define_attribute?: false` on `belongs_to_actor`.
- `mix ash.codegen` writes tenant migrations to `priv/repo/tenant_migrations/`.
  `Slapdash.Release.migrate/0` (and so `bin/migrate`) runs them in every
  tenant schema after the public migrations.

## Boundaries

- The `boundary` compiler, through `ash_boundary`, checks the references
  between parts of the portal on each build. A forbidden reference is a
  compiler warning, so `mix precommit` fails on it.
- Each Ash domain uses the `AshBoundary` extension and lists the domains it
  uses in its `boundary` block. Other modules use `use Boundary`:
  `Slapdash.Authz`, `Slapdash.Versions`, `Slapdash.Mailer`,
  `Slapdash.Secrets`, `Slapdash.Providers`, `SlapdashWeb` and `Slapdash`
  (the application, repo, vault and release tasks).
- Dependencies go one way. From the bottom: `Slapdash.Authz`;
  `Slapdash.Versions`; the domains, `Slapdash.Mailer` and
  `Slapdash.Secrets`; `Slapdash.Providers`; `SlapdashWeb`; `Slapdash`.
  The domains are, from the bottom: `Accounts`, `Instance`, `Tenancy`;
  `Connections`; `Repositories`; `Bots`; `Webhooks`.
  `boundary` rejects a dependency cycle.
- Other parts use a domain only through its public modules: the domain, and
  the resources with a `define` in the domain. Do not call an internal
  resource of another domain.
- `dirty_xrefs` lists the known exceptions. Each one has a comment that
  tells why. Do not add an exception for new code. Remove one when its
  reference moves.

## Version history

- Users, tenants, memberships, connections, repositories, bot enrollments
  and the `Slapdash.Instance` resources keep a version history with AshPaperTrail. Each create, update and destroy
  writes a snapshot, the action name and the actor to `<table>_versions`.
  `Slapdash.Versions` has the `paper_trail` block to copy into a new
  resource. Its domain needs `AshPaperTrail.Domain` with
  `include_versions? true`.
- Give the actor to every action, also with `authorize?: false`, so that
  the version records who did it.
- Keep secrets out of versions: use `sensitive_attributes :ignore` and put
  the AshCloak `encrypted_<name>` attributes in `ignore_attributes`. Never
  turn on `store_action_inputs?` on a resource that takes a secret.
- Versions of a `multitenancy strategy :context` resource stay in the
  tenant's schema, and their migrations go to `priv/repo/tenant_migrations/`.
- Only root reads versions of public-schema resources. Nothing writes
  versions except AshPaperTrail.

## Connections, repositories, webhooks and bots

`docs/explanation/bot-framework.md` tells why these parts have their shape,
and `docs/reference/bots-and-webhooks.md` lists them.

- Do not add a table, a page or an environment variable for one outside
  service. Add a provider module that implements
  `Slapdash.Connections.Provider` and the capability behaviours it has
  (`Slapdash.Repositories.Host`, `Slapdash.Webhooks.Source`), put it under
  `Slapdash.Providers`, and register it in `config :slapdash, :providers`.
- Provider code reads secrets only with `Slapdash.Connections.secrets/1`.
  The `secrets` field policy stops all other reads.
- Bots implement `Slapdash.Bots.Bot` and are registered in
  `config :slapdash, :bots`. A bot returns actions and does not call a
  service itself. Bot code must not depend on one provider: use the
  provider-neutral `Slapdash.Bots.Event`.
- Make each step safe to repeat: deliveries are unique for each delivery
  id, runs for each event id, and actions carry a key. A new action type
  needs its own idempotency rule.
- Oban job arguments hold ids only. Never put a payload, a token or a
  secret in job arguments.
- A new runner implements `Slapdash.Bots.Runner` and records its result on
  the `Slapdash.Bots.Run` through `Slapdash.Bots.Execution` or the same
  actions.
- Tests use `Slapdash.Test.FakeProvider` and `Slapdash.Test.EchoBot` from
  `test/support`, and `Req.Test` in place of real HTTP APIs.

## Security

Slapdash holds credentials (deploy keys, API tokens) and runs commands
against repositories and hosts. Treat every change as security-sensitive.

- Mark attributes holding secrets `sensitive? true` so Ash redacts them from
  errors and inspect output, and encrypt them at rest with AshCloak and
  `Slapdash.Vault` (`cloak do vault Slapdash.Vault ... end`). Never render a
  stored secret back into a form: show that one is set, and treat a blank
  field as "keep" (`Slapdash.Instance.Changes.KeepSecretWhenBlank`).
- Never log, render or put secrets in error messages, telemetry metadata or
  job arguments.
- Run external programs with `System.cmd/3` and a list of arguments. Never
  build a shell string or go through `sh -c`, and validate user-supplied
  values (repository URLs, refs, paths) before they reach a command.
- The only secret that comes from the environment is the master key. The
  keys in `config/dev.exs` and `config/test.exs` are for local use only.
- Do not send mail through a module that does `use Swoosh.Mailer`: its
  telemetry events carry the adapter config, credentials included. Use
  `Slapdash.Mailer`.

## Phoenix 1.8 conventions

- Begin every LiveView template with `<Layouts.app flash={@flash} ...>`.
  `SlapdashWeb.Layouts` is aliased in `slapdash_web.ex`, so it needs no
  extra alias.
- `<.flash_group>` lives in `SlapdashWeb.Layouts`. Only call it from
  `layouts.ex`.
- If you get errors about a missing `current_scope` assign, the route is in the
  wrong `live_session`, or `current_scope` was not passed to `<Layouts.app>`.
  Fix the routing rather than working around the assign.
- There is no icon library. When a component needs an icon, add an inline
  SVG with `aria-hidden="true"` and keep a text label or `aria-label` beside
  it.
- Use `<.input>` from `core_components.ex` for form inputs. It links errors to
  the control with `aria-invalid` and `aria-describedby`.
- Use `Req` for HTTP requests. Do not add `:httpoison`, `:tesla` or use
  `:httpc`.

## Shoddy and ShoddyPhoenix

`portal/` depends on [Shoddy](https://github.com/rellen/shoddy) and
[ShoddyPhoenix](https://github.com/rellen/shoddy_phoenix), small helper
libraries from the same author as Slapdash. Reach for them before writing a
helper of your own; their usage rules are at the end of this file.

- Read environment variables in `config/runtime.exs` with `Shoddy.Env`,
  not `System.get_env/1` plus a hand-written `raise` or `String.to_integer/1`.
- Use `Shoddy.Strings.non_blank/1` or the `is_non_empty_string/1` guard
  instead of `is_binary(v) and v != ""` checks, and `Shoddy.Parse` for user
  input.
- Every template has `ShoddyPhoenix.ControlFlow` imported (`<.choose>`,
  `<.switch>`, `<.result>`, `<.wrap_if>`, `<.each>`). Prefer them to `cond`
  and `case` blocks in HEEx.
- Every LiveView has `use ShoddyPhoenix.LiveView.Events` and
  `alias ShoddyPhoenix.LiveView`. Write event names as `event("save")` so a
  typo fails `mix compile --warnings-as-errors`, and subscribe with
  `LiveView.when_connected/2`.
- Use `Shoddy.Tests` (`eventually/2`, `put_app_env/3`) in tests instead of
  `Process.sleep/1` and hand-restored config.
- When either library has a bug or lacks something we need, do not work
  around it silently in `portal/`. Write up the fix or enhancement and report it.
  Do not push to or open issues on those repositories without approval from
  their maintainer.

## LiveView composition

- Never use LiveComponents (`Phoenix.LiveComponent`, `<.live_component>`).
  This overrides the generated Phoenix rules below, which only say to avoid
  them.
- When a LiveView needs a reusable piece of UI, reach for these in order:
  1. **Function components.** Stateless markup in a module that uses
     `Phoenix.Component`. The parent LiveView owns all state and handles the
     events.
  2. **Live widgets.** A function component for the markup, paired with a
     module that attaches the widget's state and event handling to the host
     LiveView with `Phoenix.LiveView.attach_hook/4` (`:handle_event`,
     `:handle_info`, `:handle_params`), usually from an `on_mount` callback.
     Namespace the widget's assigns and event names so several widgets can
     share one LiveView, and return `{:cont, socket}` for events that are not
     the widget's. Build widgets with `ShoddyPhoenix.LiveView.Widgets`
     (`route_events/4`, `route_instance_events/5`), attach other hooks with
     `ShoddyPhoenix.LiveView.put_hook/4`, and share PubSub topics between
     widgets with `ShoddyPhoenix.LiveView.Subscriptions`. The guide is
     `deps/shoddy_phoenix/docs/how-to/build-a-widget-with-lifecycle-hooks.md`.
  3. **Nested LiveViews** (`live_render/3`), only when the piece needs its
     own process: independent failure, its own PubSub subscriptions, or
     heavy work that must not block the parent.

## HTML, CSS and accessibility

- Use semantic HTML first. Every page has one `<main>`, plus `<header>`,
  `<nav>` and `<footer>` landmarks where they apply. Headings go in order
  without skipping levels. Use `<button>` for actions, `<a>` for navigation,
  `<table>` with `<th scope>` for tabular data, and lists for lists.
- Use ARIA only when no native element or attribute does the job, and never
  to restate native semantics. A `<div>` with a `role` is never a substitute
  for a `<button>`.
- Every form control has a visible `<label>`. Errors must be linked to their
  control with `aria-invalid` and `aria-describedby`. `<.input>` does this. If
  you write a control by hand, link its errors in the same way.
- Everything works by keyboard alone, and focus is always visible. Never remove
  focus outlines without a replacement.
- Meet WCAG 2.2 AA contrast. Never show state with colour alone. Respect
  `prefers-reduced-motion` and `prefers-color-scheme`.
- Prefer HTML and CSS to JavaScript. Reach for server-rendered LiveView and
  native elements (`<details>`, `<dialog>`, form validation attributes) before
  writing a hook. When a hook is unavoidable, write it as a colocated hook in
  TypeScript:
  `<script :type={Phoenix.LiveView.ColocatedHook} name=".MyHook" extension="ts">`.
  Standalone client modules under `assets/js/` are `.ts` files too. esbuild
  strips the types when bundling but does not type-check.
- Never add Tailwind, daisyUI or any other CSS framework or utility-class
  library. Write layered, classless CSS and build every component ourselves.
- `assets/css/app.css` declares the cascade layers in order (`reset`,
  `tokens`, `base`, `layout`, `components`, `colocated`) and imports one file
  into each. Put a rule in the lowest layer that fits. Never use
  `!important` to win a fight between layers; move the rule instead.
- Do not put `class` attributes in templates. Style elements by what they are
  (`base.css`), landmarks by their place in the page (`layout.css`), and
  components by a `data-*` attribute on their root, such as `data-flash`
  (`components.css`). Variants and state use attributes too:
  `data-variant="primary"`, `aria-invalid`, `aria-pressed`, `[hidden]`.
- Use the custom properties in `tokens.css` for colour, type, space, radius
  and motion rather than literal values. Colours use `light-dark()`, so a new
  colour token needs both a light and a dark value.
- Component-specific CSS can live next to its markup as colocated CSS, which
  lands in the `colocated` layer. That needs a module that uses
  `Phoenix.LiveView.ColocatedCSS` (none exists yet; prefer a scoped one using
  `@scope`), and the `<style :type={...}>` tag must open its template.
- The generated Phoenix rules below mention Tailwind classes. Ignore those
  parts; the rules in this file win.
- Only the `app.js` and `app.css` bundles are served. Import vendored code into
  them. Never link external scripts or stylesheets from layouts. The only
  `<script>` tags allowed in templates are colocated hooks, which are
  extracted into the bundle at compile time.

## usage_rules:otp usage
# OTP Usage Rules

## GenServer Best Practices
- Keep state simple and serializable
- Handle all expected messages explicitly
- Use `handle_continue/2` for post-init work
- Implement proper cleanup in `terminate/2` when necessary

## Process Communication
- Use `GenServer.call/3` for synchronous requests expecting replies
- Use `GenServer.cast/2` for fire-and-forget messages.
- When in doubt, use `call` over `cast`, to ensure back-pressure
- Set appropriate timeouts for `call/3` operations

## Fault Tolerance
- Set up processes such that they can handle crashing and being restarted by supervisors
- Use `:max_restarts` and `:max_seconds` to prevent restart loops

## Task and Async
- Use `Task.Supervisor` for better fault tolerance
- Handle task failures with `Task.yield/2` or `Task.shutdown/2`
- Set appropriate task timeouts
- Use `Task.async_stream/3` for concurrent enumeration with back-pressure

## phoenix:elixir usage
## Elixir guidelines

- Elixir lists **do not support index based access via the access syntax**

  **Never do this (invalid)**:

      i = 0
      mylist = ["blue", "green"]
      mylist[i]

  Instead, **always** use `Enum.at`, pattern matching, or `List` for index based list access, ie:

      i = 0
      mylist = ["blue", "green"]
      Enum.at(mylist, i)

- Elixir variables are immutable, but can be rebound, so for block expressions like `if`, `case`, `cond`, etc
  you *must* bind the result of the expression to a variable if you want to use it and you CANNOT rebind the result inside the expression, ie:

      # INVALID: we are rebinding inside the `if` and the result never gets assigned
      if connected?(socket) do
        socket = assign(socket, :val, val)
      end

      # VALID: we rebind the result of the `if` to a new variable
      socket =
        if connected?(socket) do
          assign(socket, :val, val)
        end

- **Never** nest multiple modules in the same file as it can cause cyclic dependencies and compilation errors
- **Never** use map access syntax (`changeset[:field]`) on structs as they do not implement the Access behaviour by default. For regular structs, you **must** access the fields directly, such as `my_struct.field` or use higher level APIs that are available on the struct if they exist, `Ecto.Changeset.get_field/2` for changesets
- Elixir's standard library has everything necessary for date and time manipulation. Familiarize yourself with the common `Time`, `Date`, `DateTime`, and `Calendar` interfaces by accessing their documentation as necessary. **Never** install additional dependencies unless asked or for date/time parsing (which you can use the `date_time_parser` package)
- Don't use `String.to_atom/1` on user input (memory leak risk)
- Predicate function names should not start with `is_` and should end in a question mark. Names like `is_thing` should be reserved for guards
- Elixir's builtin OTP primitives like `DynamicSupervisor` and `Registry`, require names in the child spec, such as `{DynamicSupervisor, name: MyApp.MyDynamicSup}`, then you can use `DynamicSupervisor.start_child(MyApp.MyDynamicSup, child_spec)`
- Use `Task.async_stream(collection, callback, options)` for concurrent enumeration with back-pressure. The majority of times you will want to pass `timeout: :infinity` as option

## Mix guidelines

- Read the docs and options before using tasks (by using `mix help task_name`)
- To debug test failures, run tests in a specific file with `mix test test/my_test.exs` or run all previously failed tests with `mix test --failed`
- `mix deps.clean --all` is **almost never needed**. **Avoid** using it unless you have good reason

## Test guidelines

- **Always use `start_supervised!/1`** to start processes in tests as it guarantees cleanup between tests
- **Avoid** `Process.sleep/1` and `Process.alive?/1` in tests
  - Instead of sleeping to wait for a process to finish, **always** use `Process.monitor/1` and assert on the DOWN message:

      ref = Process.monitor(pid)
      assert_receive {:DOWN, ^ref, :process, ^pid, :normal}

   - Instead of sleeping to synchronize before the next call, **always** use `_ = :sys.get_state/1` to ensure the process has handled prior messages

## phoenix:html usage
## Phoenix HTML guidelines

- Phoenix templates **always** use `~H` or .html.heex files (known as HEEx), **never** use `~E`
- **Always** use the imported `Phoenix.Component.form/1` and `Phoenix.Component.inputs_for/1` function to build forms. **Never** use `Phoenix.HTML.form_for` or `Phoenix.HTML.inputs_for` as they are outdated
- When building forms **always** use the already imported `Phoenix.Component.to_form/2` (`assign(socket, form: to_form(...))` and `<.form for={@form} id="msg-form">`), then access those forms in the template via `@form[:field]`
- **Always** add unique DOM IDs to key elements (like forms, buttons, etc) when writing templates, these IDs can later be used in tests (`<.form for={@form} id="product-form">`)
- For "app wide" template imports, you can import/alias into the `my_app_web.ex`'s `html_helpers` block, so they will be available to all LiveViews, LiveComponent's, and all modules that do `use MyAppWeb, :html` (replace "my_app" by the actual app name)

- Elixir supports `if/else` but **does NOT support `if/else if` or `if/elsif`**. **Never use `else if` or `elseif` in Elixir**, **always** use `cond` or `case` for multiple conditionals.

  **Never do this (invalid)**:

      <%= if condition do %>
        ...
      <% else if other_condition %>
        ...
      <% end %>

  Instead **always** do this:

      <%= cond do %>
        <% condition -> %>
          ...
        <% condition2 -> %>
          ...
        <% true -> %>
          ...
      <% end %>

- HEEx require special tag annotation if you want to insert literal curly's like `{` or `}`. If you want to show a textual code snippet on the page in a `<pre>` or `<code>` block you *must* annotate the parent tag with `phx-no-curly-interpolation`:

      <code phx-no-curly-interpolation>
        let obj = {key: "val"}
      </code>

  Within `phx-no-curly-interpolation` annotated tags, you can use `{` and `}` without escaping them, and dynamic Elixir expressions can still be used with `<%= ... %>` syntax

- HEEx class attrs support lists, but you must **always** use list `[...]` syntax. You can use the class list syntax to conditionally add classes, **always do this for multiple class values**:

      <a class={[
        "px-2 text-white",
        @some_flag && "py-5",
        if(@other_condition, do: "border-red-500", else: "border-blue-100"),
        ...
      ]}>Text</a>

  and **always** wrap `if`'s inside `{...}` expressions with parens, like done above (`if(@other_condition, do: "...", else: "...")`)

  and **never** do this, since it's invalid (note the missing `[` and `]`):

      <a class={
        "px-2 text-white",
        @some_flag && "py-5"
      }> ...
      => Raises compile syntax error on invalid HEEx attr syntax

- **Never** use `<% Enum.each %>` or non-for comprehensions for generating template content, instead **always** use `<%= for item <- @collection do %>`
- HEEx HTML comments use `<%!-- comment --%>`. **Always** use the HEEx HTML comment syntax for template comments (`<%!-- comment --%>`)
- HEEx allows interpolation via `{...}` and `<%= ... %>`, but the `<%= %>` **only** works within tag bodies. **Always** use the `{...}` syntax for interpolation within tag attributes, and for interpolation of values within tag bodies. **Always** interpolate block constructs (if, cond, case, for) within tag bodies using `<%= ... %>`.

  **Always** do this:

      <div id={@id}>
        {@my_assign}
        <%= if @some_block_condition do %>
          {@another_assign}
        <% end %>
      </div>

  and **Never** do this – the program will terminate with a syntax error:

      <%!-- THIS IS INVALID NEVER EVER DO THIS --%>
      <div id="<%= @invalid_interpolation %>">
        {if @invalid_block_construct do}
        {end}
      </div>

## phoenix:liveview usage
## Phoenix LiveView guidelines

- **Never** use the deprecated `live_redirect` and `live_patch` functions, instead **always** use the `<.link navigate={href}>` and  `<.link patch={href}>` in templates, and `push_navigate` and `push_patch` functions LiveViews
- **Avoid LiveComponent's** unless you have a strong, specific need for them
- LiveViews should be named like `AppWeb.WeatherLive`, with a `Live` suffix. When you go to add LiveView routes to the router, the default `:browser` scope is **already aliased** with the `AppWeb` module, so you can just do `live "/weather", WeatherLive`

### LiveView streams

- **Always** use LiveView streams for collections for assigning regular lists to avoid memory ballooning and runtime termination with the following operations:
  - basic append of N items - `stream(socket, :messages, [new_msg])`
  - resetting stream with new items - `stream(socket, :messages, [new_msg], reset: true)` (e.g. for filtering items)
  - prepend to stream - `stream(socket, :messages, [new_msg], at: -1)`
  - deleting items - `stream_delete(socket, :messages, msg)`

- When using the `stream/3` interfaces in the LiveView, the LiveView template must 1) always set `phx-update="stream"` on the parent element, with a DOM id on the parent element like `id="messages"` and 2) consume the `@streams.stream_name` collection and use the id as the DOM id for each child. For a call like `stream(socket, :messages, [new_msg])` in the LiveView, the template would be:

      <div id="messages" phx-update="stream">
        <div :for={{id, msg} <- @streams.messages} id={id}>
          {msg.text}
        </div>
      </div>

- LiveView streams are *not* enumerable, so you cannot use `Enum.filter/2` or `Enum.reject/2` on them. Instead, if you want to filter, prune, or refresh a list of items on the UI, you **must refetch the data and re-stream the entire stream collection, passing reset: true**:

      def handle_event("filter", %{"filter" => filter}, socket) do
        # re-fetch the messages based on the filter
        messages = list_messages(filter)

        {:noreply,
         socket
         |> assign(:messages_empty?, messages == [])
         # reset the stream with the new messages
         |> stream(:messages, messages, reset: true)}
      end

- LiveView streams *do not support counting or empty states*. If you need to display a count, you must track it using a separate assign. For empty states, you can use Tailwind classes:

      <div id="tasks" phx-update="stream">
        <div class="hidden only:block">No tasks yet</div>
        <div :for={{id, task} <- @streams.tasks} id={id}>
          {task.name}
        </div>
      </div>

  The above only works if the empty state is the only HTML block alongside the stream for-comprehension.

- When updating an assign that should change content inside any streamed item(s), you MUST re-stream the items
  along with the updated assign:

      def handle_event("edit_message", %{"message_id" => message_id}, socket) do
        message = Chat.get_message!(message_id)
        edit_form = to_form(Chat.change_message(message, %{content: message.content}))

        # re-insert message so @editing_message_id toggle logic takes effect for that stream item
        {:noreply,
         socket
         |> stream_insert(:messages, message)
         |> assign(:editing_message_id, String.to_integer(message_id))
         |> assign(:edit_form, edit_form)}
      end

  And in the template:

      <div id="messages" phx-update="stream">
        <div :for={{id, message} <- @streams.messages} id={id} class="flex group">
          {message.username}
          <%= if @editing_message_id == message.id do %>
            <%!-- Edit mode --%>
            <.form for={@edit_form} id="edit-form-#{message.id}" phx-submit="save_edit">
              ...
            </.form>
          <% end %>
        </div>
      </div>

- **Never** use the deprecated `phx-update="append"` or `phx-update="prepend"` for collections

### LiveView JavaScript interop

- Remember anytime you use `phx-hook="MyHook"` and that JS hook manages its own DOM, you **must** also set the `phx-update="ignore"` attribute
- **Always** provide an unique DOM id alongside `phx-hook` otherwise a compiler error will be raised

LiveView hooks come in two flavors, 1) colocated js hooks for "inline" scripts defined inside HEEx,
and 2) external `phx-hook` annotations where JavaScript object literals are defined and passed to the `LiveSocket` constructor.

#### Inline colocated js hooks

**Never** write raw embedded `<script>` tags in heex as they are incompatible with LiveView.
Instead, **always use a colocated js hook script tag (`:type={Phoenix.LiveView.ColocatedHook}`)
when writing scripts inside the template**:

    <input type="text" name="user[phone_number]" id="user-phone-number" phx-hook=".PhoneNumber" />
    <script :type={Phoenix.LiveView.ColocatedHook} name=".PhoneNumber">
      export default {
        mounted() {
          this.el.addEventListener("input", e => {
            let match = this.el.value.replace(/\D/g, "").match(/^(\d{3})(\d{3})(\d{4})$/)
            if(match) {
              this.el.value = `${match[1]}-${match[2]}-${match[3]}`
            }
          })
        }
      }
    </script>

- colocated hooks are automatically integrated into the app.js bundle
- colocated hooks names **MUST ALWAYS** start with a `.` prefix, i.e. `.PhoneNumber`

#### External phx-hook

External JS hooks (`<div id="myhook" phx-hook="MyHook">`) must be placed in `assets/js/` and passed to the
LiveSocket constructor:

    const MyHook = {
      mounted() { ... }
    }
    let liveSocket = new LiveSocket("/live", Socket, {
      hooks: { MyHook }
    });

#### Pushing events between client and server

Use LiveView's `push_event/3` when you need to push events/data to the client for a phx-hook to handle.
**Always** return or rebind the socket on `push_event/3` when pushing events:

    # re-bind socket so we maintain event state to be pushed
    socket = push_event(socket, "my_event", %{...})

    # or return the modified socket directly:
    def handle_event("some_event", _, socket) do
      {:noreply, push_event(socket, "my_event", %{...})}
    end

Pushed events can then be picked up in a JS hook with `this.handleEvent`:

    mounted() {
      this.handleEvent("my_event", data => console.log("from server:", data));
    }

Clients can also push an event to the server and receive a reply with `this.pushEvent`:

    mounted() {
      this.el.addEventListener("click", e => {
        this.pushEvent("my_event", { one: 1 }, reply => console.log("got reply from server:", reply));
      })
    }

Where the server handled it via:

    def handle_event("my_event", %{"one" => 1}, socket) do
      {:reply, %{two: 2}, socket}
    end

### LiveView tests

- `Phoenix.LiveViewTest` module and `LazyHTML` (included) for making your assertions
- Form tests are driven by `Phoenix.LiveViewTest`'s `render_submit/2` and `render_change/2` functions
- Come up with a step-by-step test plan that splits major test cases into small, isolated files. You may start with simpler tests that verify content exists, gradually add interaction tests
- **Always reference the key element IDs you added in the LiveView templates in your tests** for `Phoenix.LiveViewTest` functions like `element/2`, `has_element/2`, selectors, etc
- **Never** tests again raw HTML, **always** use `element/2`, `has_element/2`, and similar: `assert has_element?(view, "#my-form")`
- Instead of relying on testing text content, which can change, favor testing for the presence of key elements
- Focus on testing outcomes rather than implementation details
- Be aware that `Phoenix.Component` functions like `<.form>` might produce different HTML than expected. Test against the output HTML structure, not your mental model of what you expect it to be
- When facing test failures with element selectors, add debug statements to print the actual HTML, but use `LazyHTML` selectors to limit the output, ie:

      html = render(view)
      document = LazyHTML.from_fragment(html)
      matches = LazyHTML.filter(document, "your-complex-selector")
      IO.inspect(matches, label: "Matches")

### Form handling

#### Creating a form from params

If you want to create a form based on `handle_event` params:

    def handle_event("submitted", params, socket) do
      {:noreply, assign(socket, form: to_form(params))}
    end

When you pass a map to `to_form/1`, it assumes said map contains the form params, which are expected to have string keys.

You can also specify a name to nest the params:

    def handle_event("submitted", %{"user" => user_params}, socket) do
      {:noreply, assign(socket, form: to_form(user_params, as: :user))}
    end

#### Creating a form from changesets

When using changesets, the underlying data, form params, and errors are retrieved from it. The `:as` option is automatically computed too. E.g. if you have a user schema:

    defmodule MyApp.Users.User do
      use Ecto.Schema
      ...
    end

And then you create a changeset that you pass to `to_form`:

    %MyApp.Users.User{}
    |> Ecto.Changeset.change()
    |> to_form()

Once the form is submitted, the params will be available under `%{"user" => user_params}`.

In the template, the form form assign can be passed to the `<.form>` function component:

    <.form for={@form} id="todo-form" phx-change="validate" phx-submit="save">
      <.input field={@form[:field]} type="text" />
    </.form>

Always give the form an explicit, unique DOM ID, like `id="todo-form"`.

#### Avoiding form errors

**Always** use a form assigned via `to_form/2` in the LiveView, and the `<.input>` component in the template. In the template **always access forms this**:

    <%!-- ALWAYS do this (valid) --%>
    <.form for={@form} id="my-form">
      <.input field={@form[:field]} type="text" />
    </.form>

And **never** do this:

    <%!-- NEVER do this (invalid) --%>
    <.form for={@changeset} id="my-form">
      <.input field={@changeset[:field]} type="text" />
    </.form>

- You are FORBIDDEN from accessing the changeset in the template as it will cause errors
- **Never** use `<.form let={f} ...>` in the template, instead **always use `<.form for={@form} ...>`**, then drive all form references from the form assign as in `@form[:field]`. The UI should **always** be driven by a `to_form/2` assigned in the LiveView module that is derived from a changeset

## shoddy usage
_Small functions for tasks that occur frequently in Elixir code._

Shoddy is a library of small functions for tasks that occur frequently in
Elixir code. These rules tell an AI agent how to use the library correctly.
The documentation of each module gives the full description.

### General rules

- Use the standard library if it has a function for the task. Use Shoddy
  for a task that the standard library does not do in one call.
- The module names are in the plural: `Shoddy.Maps`, `Shoddy.Keywords`,
  `Shoddy.MapSets`, `Shoddy.Lists`, `Shoddy.Strings`, `Shoddy.DateTimes`.
  No module `Shoddy.Map` or `Shoddy.String` exists.
- The first argument is the value that the function operates on. Thus each
  function can be a step of a pipeline.
- A function raises `FunctionClauseError` for an argument of the wrong
  type, and `ArgumentError` for a wrong option. Do not rescue these errors.
  Correct the call.
- The functions compare with `===/2`. Thus `1` and `1.0` are two different
  keys.

### The suffix of a name

- `_if` tests a value that the function also uses. The value must be
  truthy, which means not `nil` and not `false`. Zero, `""` and `[]` are
  truthy.
- `_when` tests a condition that is a separate argument.
- `_present` tests that a value is not `nil`. Thus it keeps `false`.

Examples of these rules:

- `Shoddy.Maps.put_if/3` does not put `false`. For a field that can be
  `false`, use `Shoddy.Maps.put_present/3`.
- `Shoddy.then_if/3` takes a predicate, which is a function.
  `Shoddy.then_when/3` takes a condition that is a value. Each one raises
  `FunctionClauseError` for the other form.
- To treat `""` as no value, change it to `nil` first with
  `Shoddy.Strings.presence/1`.

### Results

- `Shoddy.Result` accepts `{:ok, value}`, `:ok`, `{:error, reason}` and
  `:error`. It does not accept a tuple of three elements. Give such a tuple
  to `Shoddy.Result.normalize/1` first.
- Use `Shoddy.Result.map_ok/2` for a function that returns a plain value.
  Use `Shoddy.Result.then_ok/2` for a function that returns a result.
- `Shoddy.Result.attempt/2` needs the option `:rescue` or the option
  `:catch`. It does not rescue each exception by default.
- The functions of `Shoddy.Parse` return `{:ok, value}` or
  `{:error, reason}`, and they examine the full text. Thus `"12px"` is an
  error. `Shoddy.Parse.integer!/2` and `Shoddy.Parse.float!/2` raise.
- The functions of `Shoddy.Env` raise an exception for an absent variable
  or a wrong value. Use them in `config/runtime.exs`, and give the option
  `:default` for an optional variable. Without a default, they raise
  `ArgumentError`, also for an absent variable. Give the option `:hint` to
  tell an operator how to correct the variable.

### Functions that an agent can use incorrectly

- `Shoddy.Tagging.reply/2` and `Shoddy.Tagging.stop/2` take the reply or
  the reason first. At the end of a pipeline of the state, use
  `Shoddy.Tagging.reply_with/2` and `Shoddy.Tagging.stop_with/2`.
- Import `Shoddy.Tagging` with the option `:only`. In a module that imports
  `Plug.Conn`, do not import `Shoddy.Tagging.halt/1`.
- `Shoddy.Maps.get_and_increment/3` returns the count after the addition,
  and not the count before it. The result is `{count, map}`.
- `Shoddy.Maps.get_or_put_lazy/3` also returns `{value, map}`. Keep the
  map, or the new entry is lost.
- `Shoddy.DateTimes.between?/3` excludes the last value of the period.
  `Shoddy.DateTimes.within?/3` includes it, and it accepts `nil` for a
  period with no end.
- `Shoddy.MapSets.toggle/2` is for an event that asks for a change. For an
  event that carries the new state, use `Shoddy.MapSets.put_or_delete/3`.
- `Shoddy.Lists.index_by/3` raises `ArgumentError` if two elements have the
  same key. The option `:on_duplicate` changes this.
- `Shoddy.Strings.truncate/3` counts graphemes, for text that a person
  reads. `Shoddy.Strings.truncate_bytes/2` counts bytes, and it is only for
  text. For binary data that is not text, use `binary_slice/3`.
- `Shoddy.Strings.upcase_first/1` keeps the rest of the string.
  `String.capitalize/1` changes the rest to lower case.
- `Shoddy.Strings.presence/1` changes only `""` to `nil`. For a field of a
  form, use `Shoddy.Strings.non_blank/1`. It also returns `nil` for a
  string of whitespace and for a value that is not a string.
  `Shoddy.Strings.blank?/1` raises for a value that is not `nil` and not a
  string.
- `Shoddy.Env.uri/2` returns the URL as a string. `Shoddy.Parse.uri/2`
  returns a `URI` struct.

### Tests

- Use `Shoddy.Tests` only in an ExUnit test. A release does not contain
  ExUnit.
- `Shoddy.Tests.suspend/1`, `Shoddy.Tests.put_app_env/3` and
  `Shoddy.Tests.put_system_env/2` restore the old state at the end of the
  test. Call them from the test process or from a `setup` callback.
- Do not use `async: true` in a test module that calls
  `Shoddy.Tests.put_app_env/3` or `Shoddy.Tests.put_system_env/2`.

## shoddy_phoenix usage
_Small functions for tasks that occur frequently in Phoenix code._

These rules give the correct use of each module of ShoddyPhoenix, and the
mistakes to avoid.

Read the documentation of a function before you use it. The source is in
`deps/shoddy_phoenix/lib`, and the guides are in `deps/shoddy_phoenix/docs`.
The site https://rellen.github.io/shoddy_phoenix/ has both.

### Setup

- ShoddyPhoenix is not on Hex. The dependency is
  `{:shoddy_phoenix, github: "rellen/shoddy_phoenix"}`.
- Each module below needs `phoenix_live_view`, version 1.2 or a later
  version before 2.0. Without that dependency, the modules do not exist.
- ShoddyPhoenix does not add Shoddy to a project. Do not call a function of
  `Shoddy` unless `mix.exs` has `{:shoddy, github: "rellen/shoddy"}`.
- Import `ShoddyPhoenix.ControlFlow` in the function `html_helpers/0` of
  `lib/my_app_web.ex`.
- Add `alias ShoddyPhoenix.LiveView` and `use ShoddyPhoenix.LiveView.Events`
  to the function `live_view/0` of that file. Add the same `use` to
  `live_component/0`.
- If the application has a component with the same name, such as a
  `switch/1`, import only the components that you use:
  `import ShoddyPhoenix.ControlFlow, only: [choose: 1, result: 1]`.

The examples below use the alias `LiveView` for `ShoddyPhoenix.LiveView`.

### Templates: ShoddyPhoenix.ControlFlow

| Component | What it renders |
| --- | --- |
| `ShoddyPhoenix.ControlFlow.choose/1` | The first `<:when>` with a truthy `test`, or `<:otherwise>` |
| `ShoddyPhoenix.ControlFlow.switch/1` | The first `<:case>` with a `value` that is equal to the `value` of the component, or `<:otherwise>` |
| `ShoddyPhoenix.ControlFlow.result/1` | `<:ok>` or `<:error>` for a result |
| `ShoddyPhoenix.ControlFlow.wrap_if/1` | Its content, inside `<:wrapper>` only when `test` is truthy |
| `ShoddyPhoenix.ControlFlow.each/1` | Its content for each item of `items`, or `<:empty>` |

These rules apply to each component:

- Only `nil` and `false` are falsy. `0`, `""` and `[]` are truthy.
- A component with no slot that matches renders nothing. It does not raise.
- A component adds no element and no whitespace. Write the list element or
  the table element around the component.

#### choose/1

HEEx evaluates the `test` of each `<:when>` on each render, also after a
truthy test. Do not write a test that is safe only after an earlier test:

```heex
<%!-- Wrong: the second test raises BadMapError for a nil user. --%>
<.choose>
  <:when test={is_nil(@user)}>Sign in</:when>
  <:when test={@user.admin?}>Admin panel</:when>
</.choose>
```

Each of these three forms is safe:

```heex
<:when test={@user && @user.admin?}>Admin panel</:when>
<:when :if={@user} test={@user.admin?}>Admin panel</:when>
<:when test={fn -> @user.admin? end}>Admin panel</:when>
```

- Keep each test cheap, and give it no side effects. Put expensive work into
  an assign.
- `:let` on a `<:when>` binds the value of its `test`.
- Use `switch/1` when each test compares one value with a constant.

#### switch/1

- The component compares with `===`. Thus `1` and `1.0` are different.
- Give each `<:case>` a literal value, such as `:loading`.

#### result/1

- The component accepts `{:ok, value}`, `:ok`, `{:error, reason}` and
  `:error`. `:let` binds the value or the reason.
- It raises `FunctionClauseError` for a value that is not a result, such as
  `nil`. For a result that can be `nil`, write `:if={@save}` on the
  component.
- Do not render a reason that is a tuple, a map or a struct. Render a message
  or a field of the reason.

#### wrap_if/1

The `<:wrapper>` must call `render_slot/1` one time with its `:let`
argument. If it does not, the content disappears, and no error occurs:

```heex
<.wrap_if test={@user.profile_url}>
  <:wrapper :let={content}><a href={@user.profile_url}>{render_slot(content)}</a></:wrapper>
  {@user.name}
</.wrap_if>
```

- A self-closing `<:wrapper />` raises `ArgumentError`.
- If only an attribute differs, such as a `class`, give that attribute an
  expression. Do not use `wrap_if/1`.

#### each/1

- Do not give a LiveView stream, such as `@streams.users`. The component
  raises `ArgumentError`.
- For a list that can be `nil`, write `items={@users || []}`.
- The component tracks the items by position, and it cannot take `:key`.
  For a long list that changes before its end, use `:for` with `:key`, and
  show the empty state with `:if`.

### Sockets: ShoddyPhoenix.LiveView

A page request mounts a LiveView two times. The first mount has a socket that
is not connected, and it runs in the process of the HTTP request. The second
mount has a connected socket. A live navigation causes only the second mount.

- `ShoddyPhoenix.LiveView.when_connected/2` applies a function to the socket
  only when the socket is connected. Use it for a subscription or a timer.
- The function must return the socket. Otherwise `when_connected/2` raises
  `ArgumentError`. `Phoenix.PubSub.subscribe/2` returns `:ok`, so return the
  socket after that call.
- Subscribe first. Then read the state that the topic changes, and assign it.
  The other order loses each change between the read and the subscription.
- Do not put an assign that the template needs into the function. The first
  mount does not call the function, and its render raises `KeyError`.

```elixir
def mount(_params, _session, socket) do
  socket =
    socket
    |> LiveView.when_connected(&subscribe/1)
    |> assign(:messages, MyApp.Messages.list_recent())

  {:ok, socket}
end

defp subscribe(socket) do
  Phoenix.PubSub.subscribe(MyApp.PubSub, "messages")
  socket
end
```

- A message can arrive for a change that the read already contains. Write
  `handle_info/2` so that such a message changes nothing. For example,
  replace an item by its id, and do not add it a second time.
- `ShoddyPhoenix.LiveView.when_not_connected/2` applies a function only in
  the first mount. Use it only to change the HTML of the HTTP response, for
  example with `Phoenix.LiveView.render_with/2`. The second mount does not
  get its assigns, and a live navigation does not call it.
- `assign_async/4` and `start_async/4` start their task only for a connected
  socket. Do not put them into `when_connected/2`.
- `ShoddyPhoenix.LiveView.put_hook/4` attaches a lifecycle hook, and it
  replaces a hook with the same id and stage. Use it in code that can run two
  times, where `Phoenix.LiveView.attach_hook/4` raises.
- `put_hook/4` puts a replaced hook at the end of its stage. If a hook of
  that stage can halt, do not replace a hook after the first attachment.

### Subscriptions: ShoddyPhoenix.LiveView.Subscriptions

Use this module when more than one part of a LiveView needs one PubSub
topic. An owner is a term that names one part, such as the key of a widget:

```elixir
socket
|> Subscriptions.subscribe(MyApp.PubSub, "chat:lobby", :left_chat)
|> Subscriptions.subscribe(MyApp.PubSub, "chat:lobby", :right_chat)
```

- `ShoddyPhoenix.LiveView.Subscriptions.subscribe/4` adds an owner. The
  LiveView has one subscription to the topic, and it receives each message
  one time.
- `ShoddyPhoenix.LiveView.Subscriptions.unsubscribe/4` removes an owner. The
  LiveView unsubscribes with the last owner.
- Use this module for each subscription to that topic. Do not also call
  `Phoenix.PubSub.subscribe/2` or `Phoenix.PubSub.unsubscribe/2` for it.
- Both functions do nothing for a socket that is not connected. They need no
  `when_connected/2`.
- Do not give the socket of a LiveComponent. Both functions raise
  `ArgumentError` for it.

### Widgets: ShoddyPhoenix.LiveView.Widgets

A widget is a part of a LiveView with its own state, events and messages. It
keeps each instance as a struct in an assign of the LiveView. The guide is
`deps/shoddy_phoenix/docs/how-to/build-a-widget-with-lifecycle-hooks.md`.

- `ShoddyPhoenix.LiveView.Widgets.route_events/4` sends each event with a
  name that starts with the name of the widget and a colon to a handler. For
  the name `"chat"` and the event `"chat:send"`, the handler gets `"send"`.
- A name is not empty, it has no colon, and it belongs to one module.
- The handler returns `{:noreply, socket}` or `{:reply, map, socket}`.
- Give the option `:actions` with the actions of the widget. The hook then
  halts each other action, and a client cannot crash the LiveView with it.
- Do not give the handler a last clause that accepts each action. Such a
  clause stops the check of `ShoddyPhoenix.LiveView.Events`.
- For a widget with instances, use
  `ShoddyPhoenix.LiveView.Widgets.route_instance_events/5`. The handler gets
  `{key, struct}` for the instance that the parameter `"instance"` names.
  The hook halts an event that names no instance.
- Do not convert a parameter of an event into an atom with
  `String.to_existing_atom/1`. Use
  `ShoddyPhoenix.LiveView.Widgets.fetch_instance/3`, which returns
  `{:ok, {key, struct}}` or `:error`.
- `ShoddyPhoenix.LiveView.Widgets.unroute_events/2` stops the events of a
  name.

```elixir
def assign_widget(socket, key) do
  socket
  |> assign(key, %__MODULE__{key: key})
  |> Widgets.route_instance_events("chat", __MODULE__, &handle_event/4, actions: ["send"])
end

defp handle_event("send", %{"message" => message}, {key, chat}, socket) do
  {:noreply, assign(socket, key, %{chat | messages: [message | chat.messages]})}
end
```

### Event names: ShoddyPhoenix.LiveView.Events

After `use ShoddyPhoenix.LiveView.Events`, write each event name of a
template with the macro `ShoddyPhoenix.LiveView.Events.event/1`:

```heex
<button phx-click={event("save")}>Save</button>
<button phx-click={JS.push(event("delete"))}>Delete</button>
```

- The compiler gives a warning for a name with no clause of `handle_event/3`
  in the module. With `mix compile --warnings-as-errors`, the warning stops
  the compile.
- To remove a warning, correct the name or add the clause. Do not add a
  clause with a variable as its first argument. Such a clause stops the check
  for the whole module.
- `event/1` accepts only a literal string. It raises `ArgumentError` at the
  compile time for a variable.
- The check does not see a plain string, such as `phx-click="save"`. It also
  does not see an event that JavaScript sends.
- In a LiveComponent, use `event/1` only for an event with
  `phx-target={@myself}`. Another event goes to the LiveView.
- A function component in another module does not know the LiveView. Write
  the name with `event/1` in the LiveView, and give it to the component as
  an attribute.
- For a widget, write `use ShoddyPhoenix.LiveView.Events, prefix: "chat"`.
  Then `event("send")` returns `"chat:send"`, and the check looks for a
  clause for `"send"` in `handle_event/3` or `handle_event/4`.
- The prefix must be a literal string, not a module attribute. Give
  `ShoddyPhoenix.LiveView.Events.event_prefix/0` to `route_events/4`, so the
  name occurs one time.

## ash_authentication usage
_Authentication extension for the Ash Framework._

# AshAuthentication Usage Rules

## Core Concepts
- **Strategies**: password, OAuth2, magic_link, api_key authentication methods
- **Tokens**: JWT for stateless authentication
- **UserIdentity**: links users to OAuth2 providers
- **Add-ons**: confirmation, logout-everywhere functionality
- **Actions**: auto-generated by strategies (register, sign_in, etc.), can be overridden on the resource

## Key Principles
- Always use secrets management - never hardcode credentials
- Enable tokens for magic_link, confirmation, OAuth2
- UserIdentity resource required for all OAuth2/OIDC strategies (stores the provider's `iss`/`sub` claims; matching users by email is unsafe)
- API keys require strict policy controls and expiration management
- Use prefixes for API keys to enable secret scanning compliance
- Check existing strategies: `AshAuthentication.Info.strategies/1`

## Strategy Selection

**Password** - Email/password authentication
- Requires: `:email`, `:hashed_password` attributes, unique identity

**Magic Link** - Passwordless email authentication
- Requires: `:email` attribute, sender implementation, tokens enabled

**API Key** - Token-based authentication for APIs
- Requires: API key resource, relationship to user, sign-in action

**OAuth2** - Social/enterprise login (GitHub, Google, Auth0, Apple, OIDC, Slack)
- Requires: custom actions, secrets, UserIdentity resource

## Password Strategy

```elixir
authentication do
  strategies do
    password :password do
      identity_field :email
      hashed_password_field :hashed_password
      resettable do
        sender MyApp.PasswordResetSender
      end
    end
  end
end

# Required attributes:
attributes do
  attribute :email, :ci_string, allow_nil?: false, public?: true
  attribute :hashed_password, :string, allow_nil?: false, sensitive?: true
end

identities do
  identity :unique_email, [:email]
end
```

## Magic Link Strategy

```elixir
authentication do
  strategies do
    magic_link do
      identity_field :email
      sender MyApp.MagicLinkSender
    end
  end
end

# Sender implementation required:
defmodule MyApp.MagicLinkSender do
  use AshAuthentication.Sender

  def send(user_or_email, token, _opts) do
    MyApp.Emails.deliver_magic_link(user_or_email, token)
  end
end
```

## API Key Strategy

```elixir
# 1. Create API key resource
defmodule MyApp.Accounts.ApiKey do
  use Ash.Resource,
    data_layer: AshPostgres.DataLayer,
    authorizers: [Ash.Policy.Authorizer]

  actions do
    defaults [:read, :destroy]

    create :create do
      primary? true
      accept [:user_id, :expires_at]
      change {AshAuthentication.Strategy.ApiKey.GenerateApiKey, prefix: :myapp, hash: :api_key_hash}
    end
  end

  attributes do
    uuid_primary_key :id
    attribute :api_key_hash, :binary, allow_nil?: false, sensitive?: true
    attribute :expires_at, :utc_datetime_usec, allow_nil?: false
  end

  relationships do
    belongs_to :user, MyApp.Accounts.User, allow_nil?: false
  end

  calculations do
    calculate :valid, :boolean, expr(expires_at > now())
  end

  identities do
    identity :unique_api_key, [:api_key_hash]
  end

  policies do
    bypass AshAuthentication.Checks.AshAuthenticationInteraction do
      authorize_if always()
    end
  end
end

# 2. Add strategy to user resource
authentication do
  strategies do
    api_key do
      api_key_relationship :valid_api_keys
      api_key_hash_attribute :api_key_hash
    end
  end
end

# 3. Add relationship to user
relationships do
  has_many :valid_api_keys, MyApp.Accounts.ApiKey do
    filter expr(valid)
  end
end

# 4. Add sign-in action to user
actions do
  read :sign_in_with_api_key do
    argument :api_key, :string, allow_nil?: false
    prepare AshAuthentication.Strategy.ApiKey.SignInPreparation
  end
end
```

**Security considerations:**
- API keys are hashed for storage security
- Use policies to restrict API key access to specific actions
- Check `user.__metadata__[:using_api_key?]` to detect API key authentication
- Access the API key via `user.__metadata__[:api_key]` for permission checks

## OAuth2 Strategies

**Supported providers:** github, google, auth0, apple, oidc, slack

**Required for all OAuth2:**
- Custom `register_with_[provider]` action
- Secrets management
- Tokens enabled
- UserIdentity resource (stores the provider's `iss`/`sub` identity claims - matching users by email or other claims is unsafe)

**How users are matched (sign-in and registration):**
- Users are resolved by the `(strategy, sub)` identity, never by email. A provider identity belongs to exactly one local user, permanently.
- A `sub` that has been seen before signs that user in.
- A new `sub` whose email matches an existing account is only linked automatically when the provider's `email_verified` claim is trusted (`trust_email_verified?`). Otherwise the behaviour depends on `on_untrusted_email_match`.
- `trust_email_verified?` defaults to `true` for GitHub/Google/Auth0/Slack/Apple and `false` elsewhere. Only enable it for providers that reliably assert email ownership.
- `on_untrusted_email_match` controls the untrusted-email-matches-existing-account case: `:reject` (the default) refuses the sign-in (the user must sign in with their existing method to link the provider); `:confirm` issues a confirmation to the existing account's email and links the provider only once the recipient proves ownership by confirming. `:confirm` requires a `confirmation` add-on (enforced at compile time).
- **Security note for `:confirm`**: confirming binds whatever provider identity initiated the flow, so the confirmation email must make clear *which* provider is being linked and that confirming grants it access — otherwise a user can be social-engineered into linking an attacker's provider account. The generated confirmation sender branches on `opts[:confirmation_type] == :identity_link` to produce this copy.

### OAuth2 Configuration Pattern
```elixir
# Strategy configuration
authentication do
  strategies do
    github do  # or google, auth0, apple, oidc, slack
      client_id MyApp.Secrets
      client_secret MyApp.Secrets
      redirect_uri MyApp.Secrets
      # auth0 also needs: base_url
      # apple also needs: team_id, private_key_id, private_key_path
      # oidc also needs: openid_configuration_uri
      identity_resource MyApp.Accounts.UserIdentity
    end
  end
end

# Required action (replace 'github' with provider name)
actions do
  create :register_with_github do
    argument :user_info, :map, allow_nil?: false
    argument :oauth_tokens, :map, allow_nil?: false, sensitive?: true
    upsert? true
    upsert_identity :unique_email

    change AshAuthentication.GenerateTokenChange

    # Required: persists the provider's `iss`/`sub` identity claims
    change AshAuthentication.Strategy.OAuth2.IdentityChange

    change fn changeset, _ctx ->
      user_info = Ash.Changeset.get_argument(changeset, :user_info)
      Ash.Changeset.change_attributes(changeset, Map.take(user_info, ["email"]))
    end
  end
end
```

### Pattern: OAuth2 with User Registration
When new users can register via OAuth2:

```elixir
actions do
  create :register_with_github do

    argument :oauth_tokens, :map, allow_nil?: false, sensitive?: true
    upsert? true
    upsert_identity :email

      user_info = Ash.Changeset.get_argument(changeset, :user_info)
```

```elixir
authentication do
```

## Customizing Authentication Actions

When customizing generated authentication actions (register, sign_in, etc.):

**Key Security Rules:**
- Always mark credentials with `sensitive?: true` (passwords, API keys, tokens)
- Use `public?: false` for internal fields and highly sensitive PII
- Use `public?: true` for identity fields and UI display data
- Include required authentication changes (`GenerateTokenChange`, `HashPasswordChange`, etc.)

**Argument Handling:**
- All arguments must be used in `accept` or `change set_attribute()`
- Use `allow_nil?: false` for required arguments
- OAuth2 data must be extracted in changes, not accepted directly

**Example Custom Registration:**
```elixir
create :register_with_password do
  argument :password, :string, allow_nil?: false, sensitive?: true
  argument :first_name, :string, allow_nil?: false
  
  accept [:email, :first_name]
  
  change AshAuthentication.GenerateTokenChange
  change AshAuthentication.Strategy.Password.HashPasswordChange
end
```

For more guidance, see the "Customizing Authentication Actions" section in the getting started guide.

## ash_boundary usage
_Boundary declarations for Ash domains, built on top of `boundary`._

# Rules for working with AshBoundary

AshBoundary derives a [`boundary`](https://hex.pm/packages/boundary) declaration
from an `Ash.Domain`'s DSL, so the compiler reports references that cross a
domain's public API.

## Setup

Add the `:boundary` compiler to the consuming project. Without it every
declaration is still computed and no violation is ever reported:

```elixir
def project do
  [
    app: :my_app,
    compilers: [:boundary] ++ Mix.compilers(),
    # ...
  ]
end
```

Extend a domain:

```elixir
defmodule MyApp.Blog do
  use Ash.Domain, extensions: [AshBoundary]

  boundary do
    deps [MyApp.Accounts]
  end

  resources do
    resource MyApp.Blog.Post do
      define :get_post, action: :read
    end

    resource MyApp.Blog.Comment
  end
end
```

## What is public

- The domain module.
- Every resource with at least one domain-level `define` in the `resources` block.
- Every type such a resource names in an attribute, a calculation or an action
  argument, when that type sits under the domain's namespace.
- Every module named in `exports` in the `boundary` block.

A resource whose only code interface is on the resource module itself
(`code_interface do ... end` inside `use Ash.Resource`) is internal. Declaring
the interface on the domain is what makes a resource public.

Exports are module-level, not function-level. A `define` publishes every public
function on that resource module. There is no way to export one action and
withhold another on the same module.

An `Ash.Type.Enum` or embedded resource named by a public resource is exported
already. `exports` covers the modules left over: a plain module a caller needs,
or a type reached through a constraint rather than named directly.

```elixir
boundary do
  exports [MyApp.Blog.Markdown]
end
```

Naming a resource of the domain there is rejected at compile time. Give it a
domain-level `define` instead.

## deps

`deps` lists the other boundaries this domain may reference. It is never
inferred, and passes straight through to `boundary`. Each entry should be a
boundary: another `Ash.Domain` extended with AshBoundary, or a module that
calls `use Boundary`. AshBoundary does not check this itself; an entry that
is not a boundary is reported by `boundary`'s own compiler, the same as it
would be for a hand-written `use Boundary, deps: [...]`.

```elixir
boundary do
  deps [MyApp.Accounts, {MyApp.Codegen, :compile}]
end
```

A bare module permits every kind of reference. `{module, :compile}` narrows it to
compile-time references, so an ordinary runtime call becomes a violation.

A dep grants access to the other domain's exports only.

## Passed through unchanged

`check`, `type`, and `dirty_xrefs` in the `boundary` block go straight to
`boundary`, exactly as they would on a hand-written `use Boundary`. AshBoundary
applies no default and no interpretation of its own to any of them; see
`Boundary`'s own docs for what each one does. Left unset, a domain gets
whatever `boundary` itself defaults to, or whatever the consuming project sets
in `mix.exs` under `boundary: [default: [check: ..., type: ...]]`.

## Relationships between domains

`boundary` does not check alias references by default, and AshBoundary sets no
`check` option of its own. A relationship (`belongs_to`, `has_many`, and so on)
naming a resource in another domain compiles to an alias reference, so it is
not checked unless the domain declares `check: [aliases: true]` itself. A
relationship in either direction, or in both directions at once, compiles
cleanly with no `deps` entry and no export required on the far side.

A `define`d call into another domain, by contrast, is a `:call` reference and
is always checked. To also enforce relationships, opt in per domain:

```elixir
defmodule MyApp.Orders do
  use Ash.Domain, extensions: [AshBoundary]

  boundary do
    deps [MyApp.Customers]
    check [aliases: true]
  end
end
```

With that set, a relationship into a non-exported or undeclared domain is
reported the same way a `:call` reference would be. Replace it with an id
attribute and a calculation that reads the other domain through its exported
interface:

```elixir
# In MyApp.Orders.Order
attribute :customer_id, :uuid

calculate :customer_name, :string, MyApp.Orders.Order.Calculations.CustomerName
```

The calculation calls a `define`d interface function on `MyApp.Customers`. Ash
passes `calculate/3` the whole batch of records, so collect the ids and make one
call rather than one call per record.

## Constraints

Resources and exported modules must be namespaced under their domain.
AshBoundary raises at compile time otherwise, because `boundary` assigns modules
to boundaries by name nesting and can neither export nor protect a module outside
the namespace.

Do not also write `use Boundary` on a domain extended with AshBoundary. Both
install a declaration and source order decides the winner, so AshBoundary rejects
it. To write the declaration by hand, drop the extension.

Domains are declared `top_level?: true`, because Ash domains do not nest inside
one another. A domain is therefore a sibling of every other boundary in the
application, whatever namespace it sits under.

## Boundaries you write by hand

A module that is not a domain, such as a Phoenix web layer, declares its own
boundary with `use Boundary`. An AshBoundary domain carries no defaults
`use Boundary` would not also carry, so the two behave the same way: set
`check: [aliases: true]` explicitly on whichever one needs alias references
checked, or a reference that only names a module goes unchecked.

To forbid a whole application, name it in `check: [apps: [...]]` and leave it out
of `deps`:

```elixir
defmodule MyAppWeb do
  use Boundary,
    check: [aliases: true, apps: [:ash]],
    deps: [MyApp.Blog, Ash.Error.Invalid]
end
```

`deps` entries are module-granular for external applications, so
`Ash.Error.Invalid` above permits that struct while `Ash.read!/1` and the rest of
`:ash` stay rejected. An entry exports only the module named; a nested error
module needs its own entry.

## Introspection

`AshBoundary.Info.deps/1` and `AshBoundary.Info.exports/1` accept a compiled
domain module or the DSL state a transformer receives.

## Clarity

With [`clarity`](https://hex.pm/packages/clarity) in the consuming project, a
"Boundary Dependencies" tab appears on every AshBoundary domain and on the
application. It holds a Graphviz diagram of the domain's `deps`, followed
recursively, rooted at that domain. Clicking a node opens that domain in Clarity.
A `{module, :compile}` dep is a dashed edge, and a dep declared by hand with
`use Boundary` is drawn as a module rather than a domain.

Domains sit in tiers by their distance from the domains that depend on nothing,
and an edge a longer path already implies is left out. A compile-time edge is
kept unless the implying path is compile-time throughout.

Nothing to configure. AshBoundary registers the content provider through its own
application environment, and `AshBoundary.Clarity.DomainDependencies` is only
compiled when `clarity` is available, so a project without it is unaffected.
